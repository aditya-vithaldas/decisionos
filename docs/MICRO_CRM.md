# Micro CRM

The application lives at `/crm` with five tabs. Fetch Mail paginates matching threads (48 per request), storing bounded account-scoped AES-GCM encrypted batches without AI calls. Repeated fetches reuse the completed baseline and append changed versions with a timestamp overlap; seven-day source snapshots can be shared by Sales, Actions and Finance. Analyze Mail exclusively makes JEV relevance/topic decisions on stored snippets: up to eight concurrent 16-thread requests, no Gmail refetch and no Gemini extraction or theme discovery. Starter clustering categories avoid discovery calls. Gemini is reserved for an explicitly requested brief reply. Fresh cards show source headers, dates and excerpts; unavailable structured company/role or finance amounts stay unknown rather than being generated. Previously grounded structured facts survive unchanged mail versions. Job deduplication requires a previously source-grounded company and position, so new cards without that identity stay separate. Sales/actions/finance use seven days, clustering fourteen, jobs keyword-filtered 180-day history: not a complete mailbox audit. Snapshot access expires after an hour, not physical deletion. Actual decisions persist encrypted and are cached for fifteen minutes. Global Done/Not important/Discard dispositions hide the exact seen version across every tab; Undo restores it and a genuine later message can reappear. Gmail is never relabeled or deleted. Only Send this reply authorizes the exact reviewed recipient/subject/body; backend once-only sending remains mandatory. Timing details separate real JEV wall time and request totals from storage and end-to-end throughput.

Google Sheets is optional and remains the source of truth for its separate board. It reads up to 2,000 customer rows and writes only mapped stage/last-contact cells. Cold starts collapsed; missing and ambiguous dates remain uncertainty. Prompt text and opportunity summaries are stored within the Google-identity-owned workspace.

## Activation

### Current shared-cache flow

The current Fetch path supersedes the per-tab source windows described above: one encrypted fourteen-day account cache serves all five tabs. Sales, Actions and Finance classify its seven-day subset; Clustering uses fourteen days. Job Hunting retains older already-grounded summaries, but new fetches do not run the previous 180-day keyword scan. That historical scan was incomplete after Gmail returned `rateLimitExceeded`; do not describe it as a complete six-month audit.

The last successful shared watermark advances only after all pages finish. Legacy seven-day caches are extended through a missing seven-to-fourteen-day gap, then a timestamp-overlapped incremental update. Active source references/versions are pruned to fourteen days; older encrypted physical records are not automatically deleted. Fetch is disabled after completion, and all tabs can Analyze without Gmail reads. A visible, signed-in page checks for changes approximately every five minutes, with a distributed account-level fetch lease, no overlapping scans and exponential retry backoff. Polling adds changed versions as Unsorted without model calls or automatic analysis. Hidden/background pages do not poll.

Analyze's full-width top bar uses actual reviewed versus eligible source counts. Uncertain decisions count as reviewed; unknown totals are indeterminate. Payment failures are a third Finance lane, with only literal source-backed amounts/currency, references, dates and action quotes. Missing metadata stays unknown and no payment action is executed.

Live uses `gemini-3.8-live`, constrained short-lived tokens and only current visible-card titles. Local ordinals, exact titles and scrolling avoid model decisions; one JEV fallback handles semantic ambiguity without acting on low-confidence targets. Audio capture starts only from the Live button. A live reply can create a brief editable draft, never an automatic send. The real provider handshake was verified; a physical microphone/voice trial is still required from the owner.

Configure a Google OAuth web client with redirect URI `https://decisionaxis.co/crm/api/oauth/callback`. Provide `CRM_GOOGLE_CLIENT_ID`, `CRM_GOOGLE_CLIENT_SECRET`, `CRM_REDIRECT_URI`, `CRM_SESSION_SECRET` (at least 32 random characters), and `CRM_TOKEN_KEY` (a base64-encoded random 32-byte key) through Cloud Run secrets. Set `CRM_FIRESTORE_PROJECT=striking-loop-447915-q3`. The service identity needs access to the default Firestore database. Credentials must stay server-side.

Use a consent screen appropriate to the intended users. Sheets read/write scope is required for a pasted spreadsheet URL and relevant cell updates. It grants access beyond the chosen sheet; the app only uses the sheet the user explicitly connects. A Google Picker/drive.file flow could reduce this scope in a later version. Gmail readonly/send is requested separately and only when the user chooses Connect Gmail; Google verification may be required for public use. Do not enable public account connections until consent configuration is complete.

OAuth uses state, PKCE, signed expiring HttpOnly cookies, and verified Google account identity. Tokens are encrypted with AES-GCM in user-specific Firestore records. Drafts belong to that same user and connected sheet. Every send requires a reviewed subject/body and explicit approval, claims the draft once using a Firestore version precondition, and updates last-contact only after Gmail confirms a message ID. An uncertain send cannot be retried automatically. Moving a card never sends mail.

## Verification and current limitations

Run `node --test test/crm-*.test.mjs`. Tests cover grounded opportunities, rejected invented rows, authenticated token storage, session expiry/tampering, OAuth state/PKCE, customer draft isolation, explicit send consent, origin checks, repeat-send prevention, and contact-date ordering. All Google/Gmail calls in tests are mocked; tests do not send real mail.

On 6 October the owner's real Google OAuth callback and Sheets preview/mapping were validated.
